# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Duck-Hack Cloud is a CRM/eCommerce base: a Node/Express/MongoDB/JWT backend plus two separate React frontends (an admin panel and a public storefront). It's deployed **single-tenant per instance** (one backend + one Mongo DB per client) — that's the committed direction, not a transitional state; see "Multi-store strategy" below for how modules get reused across stores without a shared multi-tenant backend.

## Commands

### Install
```bash
cd backend && npm install
cd frontend-admin && npm install
cd frontend-user && npm install
```

### Run locally (no Docker)
```bash
cd backend && npm start                 # http://localhost:5000, reads backend/.env
cd frontend-user && npm start           # Vite dev server on http://localhost:3000
cd frontend-admin && npm start          # Vite dev server on http://localhost:3001 (port set in vite.config.js)
```

### Run with Docker Compose
```bash
cp .env.example .env   # set STORE_SLUG (unique per store/clone) — required
docker compose up --build
```
`docker-compose.yml` derives the Compose project name, every `container_name` (`<STORE_SLUG>.backend` / `.frontend-admin` / `.frontend-user`), the internal networks and the uploads volume (`<STORE_SLUG>.backend-uploads`) from `STORE_SLUG` in the root `.env` (gitignored via `*.env`). This is what lets the repo be cloned once per store on the same host without name collisions; `compose up` fails fast if `STORE_SLUG` is unset. NPM proxy hosts **must** forward to the per-store name `<STORE_SLUG>.frontend-admin` / `.frontend-user` / `.backend` (both the `container_name` and an explicit `npm`-network alias), never to the generic Compose service names (`frontend-admin`/`frontend-user`/`backend`). The service keys are generic on purpose, but Compose still registers each as a DNS alias on the shared external `npm` network — if two stores' proxy hosts pointed at `backend`, NPM would round-robin requests between both stores' backends (was the cause of "admin of store A serves store B's bundle / intermittent 404s on /assets"). `docker compose ...` subcommands take the service name (`docker compose logs backend`); `docker ...` and `docker exec` take the container name (`docker exec <STORE_SLUG>.backend ...`).

Containers expose: frontend-admin `8080`, frontend-user `8080`, backend `5000` (no host port mappings — traffic reaches them through the external `npm` / nginx-proxy-manager network). The frontends run `nginxinc/nginx-unprivileged` (nginx as a non-root user, hence port `8080` not `80`) — if you change this, update the "Forward Port" of each proxy host in NPM. There is **no Mongo container** — point `MONGO_URL_GLOBAL` at a reachable Mongo (use `host.docker.internal` on macOS for a host-local instance). The compose file also joins an **external** `npm` network (nginx-proxy-manager); that network must already exist (`docker network create npm`) or `docker compose up` fails.

**Backend config is runtime, not baked.** The backend service uses `env_file: ./backend/.env` — the file is read when the container starts, so editing `backend/.env` then `docker compose up -d` (recreate, no `--build`) is enough. `backend/.env` is `.dockerignore`d on purpose: baking it in put secrets in image layers and, worse, the `COPY backend ./backend` layer cache would keep serving the old config after you edited the file (the symptom: a CORS/JWT change that "won't take" no matter how many rebuilds). The **frontends are the opposite** — Vite inlines `REACT_APP_*` into the static bundle at build time, so `frontend-*/.env` changes need `docker compose up -d --build`. `server.js` still calls `require("dotenv").config()` for non-Docker local dev; dotenv doesn't override vars already set by `env_file`.

### Tests
- Backend: no test suite (`npm test` is a stub that exits 1). Manual verification is via `backend/scripts/bl014-smoke-tests.sh`, a curl-based smoke test hitting a running server — configure via env vars (`BASE_URL`, `CUSTOMER_TOKEN`, `STAFF_TOKEN`, `CUSTOMER_ID`, etc.), see the script header for usage.
- Frontends: `cd frontend-admin|frontend-user && npm test` runs Vitest once (`vitest run`); `npm run test:watch` for watch mode. Only one smoke test exists (`src/App.test.jsx`) in each — no real coverage yet. Test env is jsdom, setup in `src/setupTests.js`.
- No standalone lint command. CRA's built-in `react-app` eslint went away with the Vite migration — Vite does not lint during `dev`/`build`. Add ESLint explicitly if you want it back.

### Env setup
```bash
cp backend/.env.example backend/.env
cp frontend-admin/.env.example frontend-admin/.env
cp frontend-user/.env.example frontend-user/.env
```
The backend **throws at startup** (won't boot) if `MONGO_URL_GLOBAL`, `CORS_ALLOWED_ORIGINS`, or any of the `JWT_*` vars are missing/invalid — `JWT_SECRET` must be ≥32 chars (see `server.js` and `utils/jwt.js#validateJwtEnvConfig`).

## Architecture

### Three independently deployable apps, one repo
- `backend/` — Express API, Mongoose/MongoDB, JWT auth + RBAC.
- `frontend-admin/` — React admin panel (`HashRouter`), used by staff roles.
- `frontend-user/` — React public storefront (`BrowserRouter`), used by customers.

Each has its own `package.json`, `Dockerfile`, and `.env.example`, and each is still deployed as a fully independent instance per client/store (own backend, own DB, own containers — see "Multi-store strategy" below). A change to an API shape typically means editing the backend and both frontends separately.

The repo root also has a `package.json` declaring npm **workspaces** (`backend`, `frontend-admin`, `frontend-user`, `packages/*`) — this exists solely to let the three apps consume shared internal packages under `packages/`, not to change how they're deployed; each app keeps building/running from its own folder exactly as before.

### Multi-store strategy: separated backends + shared packages (ADR in the project's Obsidian vault)
Each store/client gets its own independently deployed `backend` + DB + frontends (as today) — there is **no** shared multi-tenant backend process. To let a new module (e.g. billing) be reused by every store without rewriting it per client, reusable module code lives once in versioned internal packages and each app imports it:
- `packages/core-api/` — reusable backend modules (routes + Mongoose models); see its `README.md` for the module convention (`{ name, registerRoutes(app, ctx), models }`) that `backend/server.js` mounts, and for which modules live there today (auth, mail, storeConfig, products, inventory, orders, media, appHome, permissions — everything customer-facing/per-store) vs. what's staying in `backend/` permanently (AgencyClient/Accounting/Invoices/Infra — Duck-Hack's own internal agency-management tooling, not a per-store feature, not a candidate to move here).
- `packages/ui-kit/` — React components shared between `frontend-admin` and `frontend-user`.

This **supersedes** an earlier "Modelo B" shared-multi-tenant-backend proposal (one global admin DB + one DB per store, shared backend/frontend-admin process) — that proposal and the ADR documenting this decision are kept for history in the project's Obsidian vault, not in this repo. See "Tenant/multi-store infrastructure" below — the partial Modelo B infra that used to live here has been removed from the codebase entirely, not just deprecated.

**Branching model** (see README.md, "Publicar tiendas: flujo de ramas" for the full
workflow): `main` is canonical — all shared development happens here. Each deployed
store runs from its own `release-<store-domain>` branch, merged **only** `main →
release-*`, never the other way and never `release-* → release-*`. Don't merge a
`release-*` branch into `main`, and don't put shared-feature work directly on a
`release-*` branch — it belongs on `main` first.

**Exception: `frontend-user` changes belong on the `release-*` branch, not `main`.**
`backend`/`packages/core-api` and (mostly) `frontend-admin` are genuinely shared code
that every store's clone runs unmodified — that's what the "shared work goes to `main`
first" rule above is for. `frontend-user` is different: each store's storefront is
typically a full bespoke redesign (e.g. `release-tacita.duck-hack.cloud`'s "De Sutu
Cha'Nu" storefront — different components, different CSS, sometimes a different page
structure entirely) that diverges from `main`'s baseline far enough that even a small,
seemingly-safe change on `main` (e.g. adding one optional field to a form component)
can fail to merge cleanly into a release branch, or get silently dropped while resolving
a conflict because the file no longer looks anything like `main`'s version — this
already happened once (see git history around `frontend-user/src/components/RegisterUser.jsx`
on `release-tacita.duck-hack.cloud`). So: touch `frontend-user/` directly on each
affected `release-<store-domain>` branch, never on `main`. If a `frontend-user` change
is genuinely identical across every store (rare, and easy to be wrong about — when in
doubt, treat it as store-specific), apply it by hand on each active `release-*` branch
rather than on `main`, or promote the actually-reusable piece into `packages/ui-kit`
instead so it's imported rather than copy-pasted.

### Backend request pipeline (`backend/server.js`)
Middleware order: `express.json()` → CORS (allow-list built from `CORS_ALLOWED_ORIGINS`; throws at boot if empty; `allowedHeaders` = `Content-Type`, `Authorization`, `X-Order-Token`, `X-Appointment-Token` — any new custom request header must be added there or browsers block it at preflight with "Failed to fetch", which Node-based tests won't catch) → `helmet` (CSP disabled — this is an API-only backend, CSP is the frontends' concern) → routers mounted at `/api/agency-clients`, `/api/infra`, `/api/accounting`, `/api/invoices` (the pieces that stayed in `backend/`) → `@duck-hack/core-api` modules mounted via `coreApiModules.forEach(...)` (`/api/users`, `/api/mail`, `/api/store-config`, `/api/categories`, `/api/services`, `/api/appointments`, `/api/products`, `/api/inventory`, `/api/orders`, `/api/coupons`, `/api/cart`, `/api/loyalty`, `/api/wishlist`, `/api/promo-banners`, `/api/reviews`, `/api/media`, `/api/app-home`, `/api/permissions`) → static `/uploads` → CORS-error handler → generic error handler → 404 handler.

All error responses flow through `utils/httpResponses.js#sendError`, producing the uniform shape:
```json
{ "ok": false, "error": { "status": 400, "code": "VALIDATION_ERROR", "message": "..." } }
```
Match this convention (`status` + machine-readable `code` + human `message`) for any new endpoint.

### Auth & RBAC (`packages/core-api/modules/auth.js`, `packages/core-api/lib/authMiddleware.js`, `packages/core-api/lib/jwt.js`)
Moved here from `backend/` along with StoreConfig — see "Multi-store strategy" above. `packages/core-api/index.js` re-exports this module's `auth` object (`{createAuthMiddleware, isValidRole, ROLES, STAFF_ROLES, validateJwtEnvConfig}`); anything in `backend/` that still needs RBAC (`agencyClient.routes.js`, `accounting.routes.js`, `invoices.routes.js`, `infra.routes.js`, `validationMiddleware.js`) does `const { auth } = require("@duck-hack/core-api")`, then `auth.createAuthMiddleware(sendError)` to get `{verifyToken, authorizeRoles, authorizeSelf, authorizeSelfOrRoles}` (curried on `sendError` since the package never imports `backend/`'s error formatter directly — same injection pattern as every other module in the package).
- Roles: `super_admin`, `store_admin`, `collaborator`, `customer` (`STAFF_ROLES` = everything but `customer`). `authorizeRoles` is a flat allowlist with no hierarchy — `super_admin` must be listed explicitly in every `authorizeRoles(...)` call, not implied. `collaborator` replaced the old `catalog_manager`/`order_manager` split (see `backend/scripts/migrate-collaborator-role.mongo.js` for the one-time data migration). `super_admin` is Duck-Hack's own account (clients only get `store_admin`/`collaborator`) and always sees everything; only "Permisos" (`/admin/permissions`, `/api/permissions`) is hard-wired `super_admin`-only (otherwise a role could grant itself any module). What `store_admin`/`collaborator` can reach is **not hardcoded** — see the per-store permissions bullet below.
- **Per-store permissions** (`packages/core-api/lib/permissions.js` + `modules/permissions.js`, `/api/permissions`): the admin is sold per client, so each deployment has a `StorePermissions` singleton with two layers — `enabledModules` (what the store paid for) and `roles.{store_admin,collaborator}` (what each role may use). Access = contracted AND allowed for the role; `super_admin` bypasses; turning a module off keeps the role checkboxes for when it's re-enabled. Modules: `panel` (the `/admin` index dashboard, `AdminMenu.jsx` + `/api/infra/*` — server usage and Duck-Hack infra links), `storeConfig`, `appConfig` ("Configurar App", `/admin/app-config/*` + `/api/app-home` admin routes), `services` (service catalog + service categories — `/api/categories` authorizes by `kind`), `abandonedCart` (abandoned-cart email job + generated personal coupons, `/admin/abandoned-cart`), `promoBanner` (promo banners with dates and a category/coupon/URL target, public `GET /api/promo-banners/public?placement=home|shop` — hidden when the coupon/category no longer works; `/admin/promo-banners`), `wishlist` (back-in-stock email for favorites — a scheduled job watches `User.favorites` products' availability; storefronts must serve `FRONTEND_URL/tienda/<productId>`, the link it carries; `/admin/wishlist`), `loyalty` (points per paid order redeemable at checkout + stamp card per completed appointment, `/admin/loyalty`; logic in `lib/loyalty.js` hooked into orders/appointments, only runs when contracted *and* the program is enabled in its settings), `reminders` (appointment reminder emails — a scheduled job; settings live in "Ajustes de agenda", no page of its own), `appointments` (agenda — FullCalendar in `frontend-admin`'s `AppointmentCalendar.jsx`, lazy-loaded route —, specialists, time blocks, agenda settings, customer/business emails with `.ics` via `lib/ics.js`; storefronts that sell appointments must implement `FRONTEND_URL/cita/<id>?token=…` (plus `&accion=confirmar` from the reminder and `&accion=calificar` from the post-appointment review email → `POST /api/reviews/appointment`), the link those emails carry; inside it, management is super_admin/store_admin only and a collaborator only sees the specialist linked to her account — nav entries flagged `managers` in `MODULE_NAV`), `products`, `inventory`, `orders`, `coupons`, `reviews`, `media`, `users`, `agencyClients`, `accounting` (also Movimientos), `invoices` — the Duck-Hack agency modules are sellable too. With no doc saved, `DEFAULT_PERMISSIONS` reproduces the old hardcoded behavior (everything contracted; `store_admin` = everything but `panel`/`appConfig`; `collaborator` = products/inventory/orders/media/appointments), so upgrading a deployed store changes nothing. A **new module key** (e.g. `services`, `appointments`) is therefore *on* only for stores that never saved permissions (they run on `DEFAULT_PERMISSIONS`); a store that already saved its `StorePermissions` doc gets it *off* (not in its `enabledModules`, backend 403) until the super_admin enables it in Permisos — check both cases when a store gets the `main → release-*` PR. Enforced server-side on every staff route via `createModuleAuthorizer({ mongooseConnection, sendError })` → `authorizeModule(key, { alsoBy, requireContract })` / `authorizeModuleAccess({ module, readAlso })` / `authorizeSelfOrModule(idParam, key)` (`403 MODULE_NOT_ALLOWED`) — `backend/routes/*` get it from `require("@duck-hack/core-api").permissions` with `mongoose.connection`. Cross-module reads: products readable by inventory/orders/appConfig and media list/upload by products/storeConfig/appConfig/promoBanner even if not contracted (catalog is public, pickers are infrastructure); agency modules read each other only if the read module is contracted. Config is cached in memory per connection (invalidated on save, 60 s TTL). In Users, nobody but `super_admin` can view/create/edit/assign a role ranked above their own (`roleRank`: customer < collaborator < store_admin < super_admin) — this replaces the old "store_admin can't touch super_admin" checks. `GET /api/permissions/me` feeds `frontend-admin`'s `PermissionsProvider` (`hooks/usePermissions.jsx`); `PermissionsManager.jsx` (`/admin/permissions`) is the super_admin editor. When you add a new admin module: add its key to `PERMISSION_MODULES` (and `DEFAULT_PERMISSIONS`), guard its routes with the authorizer, and add it to `frontend-admin/src/utils/permissions.js#MODULE_NAV` (its menu entries), to a group in `NAV_GROUPS` (the collapsible sidebar sections), and `App.jsx` `gate(...)`.
- JWT is HS256 with required issuer/audience/expiry. JWT types (`access`, `email_verification`, `password_reset`, the guest `order_access` / `appointment_access` tokens and the unsubscribe `email_preferences` token) are distinguished by a `tokenType` claim so one can't be replayed as another.
- Refresh tokens (long sessions, built for the mobile app; the web ignores them) are **not** JWTs: `POST /api/users/login` also returns an opaque `refreshToken`, stored only as a SHA-256 hash in the `RefreshToken` collection (TTL index on `expiresAt`, lifetime `JWT_REFRESH_EXPIRES_IN`, optional, default `30d`). `POST /api/users/refresh` rotates it (old one revoked; reusing a rotated token after a 30 s grace revokes the whole session/`family`), `POST /api/users/logout` revokes one session, and password change/reset and account deletion revoke all of a user's sessions. Logic in `packages/core-api/lib/refreshTokens.js` + `modules/auth.js`. Access tokens stay stateless — revoking a refresh token doesn't kill an already-issued access token before it expires.
- Composable middlewares: `authorizeRoles(...roles)`, `authorizeSelf(idParam)`, `authorizeSelfOrRoles(idParam, ...roles)` — chain these after `verifyToken` on route definitions instead of writing ad hoc role checks in handlers.
- `POST /api/users/register` always forces `role: customer` server-side. Role changes only happen via `PUT /api/users/:id` with extra guardrails: no self-promotion, `store_admin` can't view/edit/assign `super_admin`.

### Scheduled jobs (`packages/core-api/lib/scheduler.js`, `lib/notify.js`)
In-process scheduler, one per backend instance (stores are single-instance, so no external queue). Modules may export `registerJobs(scheduler, ctx)` next to `registerRoutes`; `backend/server.js` builds a shared `coreApiCtx`, registers every module's jobs and starts the scheduler on Mongo `open`. Jobs never overlap themselves, failures are logged and isolated, nothing runs while Mongo is disconnected. Use `claimEach` to send a notice exactly once (atomic "mark before send" on a `*SentAt`-style field, mark released + attempt counted on failure, max 3) — never a find-then-send loop. `SCHEDULER_ENABLED=false` turns it off (tests; and if a store ever runs >1 backend instance, only one may have it on); `SCHEDULER_JOB_INTERVAL_MS` overrides every job's interval (tests only). A job for a sellable feature must check `lib/permissions.js#isModuleContracted(connection, key)` itself (there's no request/user to authorize) — e.g. appointment reminders run only if `reminders` is contracted. Notices go through `notify({ channel })`: `email` only; WhatsApp/SMS are `registerChannel` hooks for a future provider.

### Validation & rate limiting
- `middleware/validationMiddleware.js`: one hand-written `validateXPayload` function per request shape (no Joi/Zod) that trims/normalizes `req.body` in place and calls `next()`. Follow this pattern for new endpoints rather than introducing a schema library. Only what's left in `backend/` lives here now (AgencyClient/Accounting/Invoices) — Auth's and StoreConfig's validators moved with them into their `packages/core-api` module files.
- **Phones are Mexican, 10 digits** (the platform is Mexico-first): every phone field (users, addresses, orders, appointments, store contact/legal/SPEI/team, agency clients) goes through `packages/core-api/lib/phone.js#parseMxPhone` — strips separators and a `+52`/`52`/`521` prefix, stores only the 10 digits, anything else is `400 VALIDATION_ERROR`. WhatsApp is captured as 10 digits and stored as `52` + 10 (`toWhatsappPhone`) because the storefront builds `wa.me` links from it. `backend/` validators get it via `require("@duck-hack/core-api").phone`. In `frontend-admin`, use `components/PhoneInput.jsx` (or `type: "mxPhone"` in `StoreConfigListEditor` fields) for any new phone input.
- `packages/core-api/lib/rateLimit.js#createRateLimiter`: in-memory per-IP limiter (keyed off `X-Forwarded-For`/`req.ip`). Resets on process restart and does **not** coordinate across multiple backend instances — fine for single-instance deploys, not for horizontal scaling. `backend/middleware/rateLimitMiddleware.js` is gone — this was its only consumer's replacement (register/login rate limits, in `modules/auth.js`; the contact-form limit already lived here from the Mail move).

### Media uploads (`packages/core-api/lib/uploads.js`, `packages/core-api/modules/media.js`)
Multer buffers the upload in memory → type is decided by content, never by the client's declared `Content-Type`: JPEG/PNG are decoded and re-encoded by `sharp` (strips unexpected metadata), GIF is written as-is (sharp would flatten the animation), MP4/WebM are recognized by their binary signature and written as-is → saved under `UPLOADS_DIR` (falls back to `/tmp/media-uploads` if that's not writable). Two factories: `createMediaUploadMiddlewares` backs `POST /api/media`, the **only** upload path the admin uses (logo, team/testimonial photos, hero image/GIF/video and product images all go through the media library via `frontend-admin`'s `MediaPicker`/`MediaField`); `createSingleImageUploadMiddlewares` only remains for the customer profile photo (`PUT /api/users/:id`, `auth.js`); `createPaymentProofUploadMiddlewares` handles SPEI payment proofs (JPG/PNG re-encoded, PDF by signature) and writes them to `UPLOADS_DIR/private/payment-proofs/` (`resolvePrivateDir`) — same persistent volume, but `server.js` blocks `/uploads/private` (decoded + normalized path, case-insensitive) before `express.static`, and the files are only streamed by the authenticated order routes. Never move private files under the public root without that guard. The old per-feature endpoints (`/api/uploads/products-image`, `/api/store-config/upload-image`, `/api/store-config/upload-hero-image`) were removed. `/api/media` treats the disk as the source of truth for which files exist; the `Media` collection only stores editable metadata (title, alt text) — "renaming" never moves the file, so paths stored in `Product.images`/`StoreConfig`/`User.profileImage` don't break. `backend/middleware/imageUploadMiddleware.js` is gone; `backend/utils/uploads.js` still exists but only for `server.js`'s static `/uploads` serving (`resolveUploadsDir()`), not for the upload pipeline anymore.

### Tenant/multi-store infrastructure (removed)
The old "Modelo B" proposal (one global admin DB + one DB per store, shared multi-tenant backend) is superseded — see "Multi-store strategy" above for the current direction; the full ADR lives in the project's Obsidian vault, not in this repo. The partial Modelo B infra (`utils/dbConnectionManager.js`, `scripts/tenant-bootstrap.mongo.js`, the `TENANT_*` env vars, the `X-Tenant-Slug` header `frontend-user/src/utils/apiClient.js` used to send) was never consumed by any route/model and has been **deleted** from the codebase, not just deprecated — don't look for it. `backend/scripts/storeconfig-bootstrap.mongo.js` is unrelated (it predates Modelo B and seeds the single per-deployment `StoreConfig` doc) and is still the script to use.

Every model — `User`, `RefreshToken`, `StoreConfig`, `Category`, `Service`, `Specialist`, `TimeBlock`, `AppointmentSettings`, `Appointment`, `Product`, `Inventory`, `Order`, `Coupon`, `Cart`, `AbandonedCartSettings`, `LoyaltySettings`, `LoyaltyAccount`, `LoyaltyLedger`, `WishlistSettings`, `ProductStockState`, `WishlistNotice`, `PromoBanner`, `Review`, `Media`, `AppHome`, `StorePermissions` (via `packages/core-api/lib/moduleHelpers.js#getOrCreateModel(ctx.mongooseConnection, ...)`) and `AgencyClient`/`Transaction`/`Invoice`/`HostingPayment`/`DesignDebt` (via direct `mongoose.model(...)`, still in `backend/models/`) — registers against the same single per-instance connection opened once in `server.js`. There is no tenant resolver, no `req.tenant`, and none is planned; that's the point of the current direction (see "Multi-store strategy").

`StoreConfig` is a deliberate singleton per deployment (`singletonKey: "default"`, unique + immutable) — the `/api/store-config` routes always read/write that one document. `AppHome` (`packages/core-api/modules/appHome.js`) follows the same singleton pattern: the mobile app's home screen as server-driven JSON (`sections`, array order = screen order), edited in `frontend-admin`'s "Configurar App" → Home tab (`appConfig` permission module, by default `super_admin` only) (`/admin/app-config/home`, `AppConfigTabs.jsx` + `AppHomeEditor.jsx`, visual + raw-JSON views; save = publish; new app settings get their own tab there). `GET /api/app-home/public` returns visible sections only, with product carousels pre-resolved via `lib/purchaseLimits.js#filterInStock` (same active + in-stock rule as `/api/products/public`). Sections are stored as `Mixed` and validated by hand against a type catalog (`SECTION_VALIDATORS`; mirrored for the editor in `frontend-admin/src/utils/appHomeSections.js`) — adding a section type means updating both, and the app must ignore unknown types so older app versions keep working. The `store*` section types (`storeHero`, `storeMetrics`, `storeCommands`, `storeServices`, `storePricingPlans`, `storeFaqs`, `storeTeam`, `storeTestimonials` — `STORE_CONTENT` in `appHome.js`) hold no content of their own: they reuse the matching `StoreConfig` array (edited once in "Configurar tienda", shown the same on web and app), resolved in `/public` as `items` (active only, by `sortOrder`; live metrics via `lib/liveMetrics.js#resolveLiveMetrics`, shared with `/api/store-config/public`).

### Frontend patterns
- Both frontends read the backend base URL from `REACT_APP_HOST_SERVICES_URL` and call it directly — `frontend-admin` uses `axios` inline per-component, `frontend-user` goes through `utils/apiClient.js#apiFetch`, which unwraps the backend's `{ ok, error }` envelope into a thrown `Error(message)`.
- `frontend-admin` keeps the session in `localStorage` (`token`, `role`, `name`); which screens a staff user sees comes from `GET /api/permissions/me` via `PermissionsProvider` (`hooks/usePermissions.jsx`) — `App.jsx` wraps each route in `gate(moduleKey, element)` (Loader while permissions load, redirect to `/admin` otherwise) and `AdminShell.jsx` builds the menu from `utils/permissions.js#navGroupsFor` (`NAV_GROUPS` → collapsible sections Configuración / Servicios / Tienda / Agencia over `MODULE_NAV`'s entries, plus Usuarios + Permisos down in the session block next to "Cerrar sesión" (`bottom: true`); a group with a single visible entry renders as a plain link, the active group auto-opens, open state remembered in `localStorage`). `/admin` (index) is the Panel when `can("panel")`, otherwise it redirects to the user's first allowed module; only "Permisos" uses `superOnly(...)`. `utils/roles.js` keeps just the role enum/labels, `STAFF_ROLES` (who may log in) and `assignableRolesFor` (role rank for user forms).
- `frontend-user` renders most sections (`Inicio`, `AboutUs`, `OurServices`, `Services`, `Customers`, `ContactUs`) together on a single scrolling `"/"` route, plus a few standalone routed pages (`legal-notice`, `privacy-policy`, `users/verify`, `login`, `register`). `react-scroll` + the `ScrollToSection` component in `App.js` handle in-page hash anchors.

### API contract source of truth
`backend/openapi.yaml` documents the live contract and is the only architecture/API doc kept in this repo — everything else (interface contracts, the API change-proposal process/template, historical backlog) lives in the project's Obsidian vault. Keep `openapi.yaml` in sync when routes change.
